# 探针工具箱：在黑箱游戏引擎中建立 API 发现体系

## 问题

The Sims 4 是一个封闭的商业游戏。它没有公开 API 文档，Python 运行时嵌在游戏引擎内部，数万个对象和数十万属性在内存中运行——但开发者完全不知道"什么东西在哪个类上"。

需要采集某个数据（比如角色的技能等级、物品的可用交互），传统做法是：

```
猜属性名 → 写脚本 → 进游戏测试 → 报错 → 换名字再试 → ...
```

每次循环需要重启游戏、加载存档、触发场景。一个属性定位可能花半小时。

## 核心洞察

**面对黑箱系统，先造探索工具，再用工具回答具体问题。**

不要每次需求都进游戏试。一次性把运行时的类型和属性面全扫出来，建成可搜索的静态目录。之后任何数据需求不再是"进游戏试"，而是 `grep` 一把，5 秒定位。

## 图书馆（ai_probe_library）

**做什么：** 遍历游戏 Python 运行时的对象图，按类型去重，记录每个类的全部属性名和类型签名。最终产出 `types_index.txt`——423 个类型、28,571 个属性的可搜索目录。

**怎么做的：**

1. 从已知入口点出发（`services`、`sim_info`、`zone`、`household` 等）
2. BFS 遍历对象引用，跳过已见过的类型
3. 对每个新类型，内省全部属性（`dir()` + 类型推断）
4. `alarm` 分片执行——不冻游戏主线程，不触发 watchdog 超时
5. 落盘到 `MythicaData/api_library/`，可被任何工具 grep

**关键设计：** `stop` 参数可随时中止并保留已扫描结果。4 秒跑不完？没关系，能跑多少是多少，下次继续。

**使用方式：** "能不能采到角色的生活方式的名称？"

```bash
grep "lifestyle" MythicaData/api_library/types_index.txt
# → SimInfo.lifestyles: list[Lifestyle]
# → Lifestyle.name: str
```

5 秒。不需要进游戏。

## 结构树（ai_probe_tree）

**图书馆的局限：** 它是扁平的。知道 `SimInfo` 有 `household` 属性，但不知道 `household` 下面还有什么、`SimInfo` 本身又是从哪里挂下来的。数据层级关系——"谁包含谁"——在扁平索引中完全丢失。

**做什么：** 从指定入口点出发，DFS 遍历对象引用，输出缩进树状图，保留完整包含路径。

```
services
├── sim_info_manager
│   └── SimInfo (×8)
│       ├── household: Household
│       │   ├── name: str
│       │   └── members: list[SimInfo]
│       ├── career: Career
│       │   ├── company_name: str
│       │   └── level: int
│       └── skills: list[Skill]
└── zone_manager
    └── Zone
        ├── lot: Lot
        └── objects: list[GameObject]
```

**两个关键工程决策：**

1. **同类型只展开一次。** 场景中有 8 个 Sim，每个 Sim 都有 `household`、`career`、`skills`。如果每个都展开，树会爆炸成不可读的冗余结构。按类型去重后，暴露的是**架构设计**，不是**数据重复**。

2. **alarm 分片后台执行。** DFS 可能触碰数万个对象，必须异步。每个分片跑固定时限，超时自动挂起、下一个 alarm tick 继续。既不冻主线程，又不怕被游戏引擎的 watchdog 杀掉。

**图书馆 + 结构树的关系：**

| | 图书馆 | 结构树 |
|---|---|---|
| 回答 | "X 在哪个类上" | "谁包含谁" |
| 结构 | 扁平索引 | 树状图 |
| 用途 | 快速查属性位置 | 理解数据架构 |
| 去重 | 按类型 | 按类型 + 按层级 |
| 适合 | 日常采集需求 | 理解新子系统 |

## 方法论抽象

这套方法不限于 Sims 4。任何需要在**没有文档的 Python 运行时**中建立 API 理解的场景都适用：

1. Legacy 代码库迁移——先建运行时目录，再决定迁移策略
2. 第三方闭源 SDK 集成——先扫描再对接
3. 大型框架（Django、Unity、Unreal Python binding）的运行时发现

核心原则不变：**先造工具，再问问题。一次性投资，永久减少搜索成本。**

---

> 完整探针体系包含四层（表面扫描 → 定向深读 → 差分定位 → 图书馆索引）和运行时交互探针（物品/社交/系统），另有开发闭环和自主观察器。本文仅聚焦两大核心工具的方法论。
