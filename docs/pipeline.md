# AI 叙事管线 — 长上下文叙事的状态管理

不是让 AI 写小说，是让 AI 在数百轮交互中保持叙事连贯性。

---

## 问题

LLM 每次调用是**无状态**的。给它一段 prompt，它生成一段文本。下一次调用时，它不记得上次写了什么。

如果在游戏中跑一个持续数小时的叙事——角色关系在变化、身体状态在演进、事件在累积——每次都把全部历史塞进 prompt 是不可行的。token 窗口不够，成本爆炸，而且 LLM 在超长上下文里会"迷失"——忘了该聚焦什么。

这个管线要解决的问题是：**在几十到几百轮 LLM 调用中，让每一轮的故事自然接续上一轮，像一个连贯的叙事线程。**

---

## 两条管线

项目有两条独立的叙事管线：

| | Story（故事） | Inner Voice（内心独白） |
|---|---|---|
| **触发方式** | 游戏存档事件 → 文件监控 → 桌面端拉起 | 游戏内交互事件 → HTTP 实时推送 |
| **频率** | 分钟级，事件驱动 | 秒级，概率触发 |
| **视角** | 第三人称叙事 | 第一人称内心声音 |
| **消费方** | 游戏内故事记录 + 人类阅读 | 游戏内弹窗通知 + 历史存档 |
| **关系** | 独立运行，共享部分格式概念但数据不交叉 | |

两者架构镜像——都是三阶段管线 + Baton 接力——但实现独立，互不干扰。

---

## 三阶段管线

每次生成拆成三次独立的 LLM 调用：

```
Phase 1 → Phase 2 → Phase 3 → 存储 → 输出
(生成)    (校验)    (解析)
```

### Phase 1 — 正文生成

**只做一件事：写散文。** 不写标题、不写标记、不提取结构化数据。

为什么不让 LLM 一次性生成正文 + 标记？试过。结果是 LLM 在"创作"和"整理"两种思维模式之间来回切换——正文质量下降，标记格式也经常出错。拆开后：写作 AI 专注写作，解析 AI 专注解析。各自在自己的模式下工作。

Phase 1 的 prompt 注入：
- **DATA 块**：从游戏状态构建的实时数据（角色属性、关系、环境）
- **STATE 块**：上一轮的状态提取（进度、轨迹、身体状态、冻结定格）
- **BATON 块**：接力信息——上一轮的"下一秒"是这一轮的起点
- **RULES 块**：写作规则（人类可编辑）
- **记忆块**：跨轮累积的关系锚点、心事、接待记录

### Phase 2 — 校验与提取

**不看正文质量，只提取结构化标记。** 读取 Phase 1 的完整正文，从中提取：

- **STATUS**：五选一场景阶段分类（日常 / 过渡 / 事件前 / 事件中 / 事后）
- **BATON**：接力信息——冻结定格 + 下一秒（接续起点）
- **STATE**：状态字段（进度、轨迹、过程、身体、衣着、环境、冻结、下一秒）
- **关系锚点**：人物关系变化的简短标记

Phase 2 的关键职责是**去重检测**：如果产出的"下一秒"和上一轮完全相同 → 说明 AI 在重复自己 → 触发重试。

### Phase 3 — 结构化解析

**不看正文，只看 Phase 2 的输出。** 将标记块解析为结构化数据，补充：

- TIME：叙事时刻
- SUMMARY：摘要
- MENTAL：角色心理状态
- ROSTER：客户名册（来访者管理）
- BURDEN：心事（未解决的情感锚点）
- 推理链：AI 的决策依据

Phase 2 缺失的标记（罕见但可能），Phase 3 顺带兜底——零额外 API 调用。

### 为什么是三阶段而不是一阶段

| 方案 | 问题 |
|------|------|
| 一阶段（正文+标记一起出） | LLM 在"创作"和"整理"之间切换，两边都做不好 |
| 两阶段（正文 → 结构化提取） | 去重检测放在哪？放在 P1 太重，放在 P2 太晚 |
| **三阶段**（选中方案） | 写作/校验/解析各司其职。P2 是"质检关"——不通过就重试，保护 P3 不受坏数据污染 |

## Baton 接力 — 跨轮连贯性的核心

这是整个管线最重要的设计。

**概念：每一轮叙事结束时，AI 产出一个"下一秒"——此刻卡在什么动作/情绪的什么位置。下一轮的 prompt 从这个"下一秒"开始接续。**

```
第 N 轮：
  正文：...他的手停在半空，不知道该不该碰她。
  Baton: 下一秒: 他的手指终于落下——轻轻触到她的肩膀

第 N+1 轮：
  prompt 注入：{上一轮终点} = "他的手指终于落下——轻轻触到她的肩膀"
  正文：她像被烫到一样往后缩，又停住。...
```

这不是简单的"把上一段摘要喂进去"。Baton 是一个**精确的叙事悬停点**——不是概括这一段写了什么，而是标记"故事卡在哪个节拍上"。接力时，LLM 从那个节拍开始继续，而不是从概括出发重新编。

### Baton 的三种悬停类型

| 类型 | 含义 | 示例 |
|------|------|------|
| 动作悬停 | 故事卡在一个物理动作的半拍 | "他伸出的手悬在半空，距离她的肩膀还有三厘米" |
| 心理悬停 | 故事卡在一个情绪/决策的临界点 | "她脑子里一片空白，只知道不能回头" |
| 对话悬停 | 故事卡在一句话的开头或结尾 | "'我——' 话到嘴边又吞了回去" |

不同类型的悬停需要不同的接续方式。动作悬停从身体感觉接，心理悬停从情绪推演接，对话悬停从下一句接。

### 断裂检测

每次收到新结果时，比较"上轮承诺的下一秒"和"本轮 AI 实际收到的起点"——不一致则输出 `BATON MISMATCH` 告警。

---

## 四组件持久化

每轮叙事结束后，四个接力组件写入磁盘：

| 组件 | 内容 | 作用 |
|------|------|------|
| **BATON** | 冻结定格 + 下一秒 | 下一轮的叙事起点 |
| **STATUS** | 五选一场景标签 | 判断叙事处于哪个阶段（决定接续策略） |
| **STATE** | 进度/轨迹/过程/身体状态 | 下一轮的物理/位置上下文 |
| **MENTAL** | 角色内心状态 | 下一轮的情绪连续性 |

四个组件采用**内存主线 + JSON 兜底**模式：正常运行走内存（快），崩溃恢复走 JSON（有备份）。

---

## 崩溃哲学：不可信的状态比没有状态更危险

**决策：管线崩溃后，不恢复、不补录、不标记。清空残留数据，等游戏端自然产生新交互后重新走完整流程。**

为什么：LLM 调用过程中崩了——你不知道它写到哪一步了。解析崩了？正文崩了？标记崩了？半成品的 STATE 里有几个字段是对的、几个是空的？猜错一个，下一轮就从错误的状态接续，然后连锁污染。

恢复一次的调试成本足够重新生成十次。更关键的是：**这次崩了，下次还会崩**——崩溃的根因（prompt 太长？AI 返回格式变了？）不会因为"努力恢复"而消失。直接丢弃、等下一轮自然触发——相当于给了系统一个干净的起点。

## 两个关键设计原则

### 1. 写作和解析必须分家

同一段 AI 输出，Phase 1 只看"写得好不好"，Phase 2/3 只看"标记对不对"。两个判断标准会互相干扰——如果让一个 AI 同时做两件事，它会为了标记格式牺牲正文质量，或者为了正文流畅忘了标记规范。

### 2. 标签格式极简

AI 输出的标签种类不超过 5 种，子变体为 0。增量语义（"只写变化的部分"）的复杂度放在代码层——同名合并、交叉校验、新旧对比——不转嫁给 AI。

**血案：** 曾给 AI 5 种增量标签前缀 → AI 自行衍生 3 种不支持的变体 → `[已毕] [→已已毕]` 怪格式链。教训：给 AI 的格式选择越多，它自创变体越多。AI 擅长生成内容，不擅长遵守格式规范。

## 数据流全景

```
游戏端                    桌面端 Mythica                   AI API
┌──────────┐         ┌─────────────────────────┐         ┌──────┐
│ 交互事件  │  HTTP   │ Phase 1: 组装 prompt     │  API    │      │
│ 数据采集  │ ──────► │   DATA + STATE + BATON  │ ──────► │ LLM  │
│          │         │   + RULES → 正文生成      │         │      │
│          │         │                          │ ◄────── │      │
│          │         │ Phase 2: 正文 →           │         └──────┘
│          │         │   ||STATUS|| + ||BATON||  │         ┌──────┐
│          │         │   + 去重检测               │  API    │      │
│          │         │                          │ ──────► │ LLM  │
│          │         │                          │ ◄────── │      │
│          │         │ Phase 3: 标记 →           │         └──────┘
│          │         │   结构化数据 + 推理链      │
│          │         │                          │
│          │         │ 写 signal + JSON          │
│ 信号轮询  │ ◄────── │ (BATON/STATE/MENTAL 持久化)│
│ 弹窗展示  │  文件    │                          │
└──────────┘         └─────────────────────────┘
```

## 与沙盘的关系

叙事管线和沙盘引擎是项目中**并行运行的两套 AI 系统**：

| | 叙事管线 | 沙盘引擎 |
|---|---|---|
| **问题** | "故事在发生什么？" | "角色该做什么？" |
| **产出** | 散文 + 结构化标记 | 可执行的动作命令 |
| **方向** | 游戏 → 桌面（单向） | 游戏 ↔ 桌面（双向） |
| **频率** | 事件驱动，分钟级 | 持续循环，秒级 |

两者共享数据源（游戏端的同一份数据采集），但决策完全独立。一个角色可以同时在故事里"内心纠结"、在沙盘里"去上厕所"——叙事和行动互不阻塞。

---

> 这套管线经过了半年的迭代：从单次调用到三阶段，从无状态到 Baton 接力，从崩溃后手动恢复到"丢弃不恢复"原则。每次简化都是在删掉"聪明但不可靠"的东西。
